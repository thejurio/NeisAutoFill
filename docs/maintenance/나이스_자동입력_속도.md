# 나이스 자동입력 속도 — 무엇이 느렸고, 더 줄이려면

- 마지막 실측: 2026-08-20 (전주덕일초 2026학년도 2학기 5학년 1반)

---

## 결론부터

느렸던 것은 나이스도, 네트워크도, 클릭 방식도 아니었다. **우리가 넣어 둔 고정 대기**였다.

| | 전 | 후 | 실제 걸리는 시간 |
|---|---|---|---|
| 메뉴 열고 닫기 | 1591 ms | **130 ms** | 메뉴는 91 ms 에 뜬다 |
| 주차 이동 | 1570 ms | **245 ms** | 화면은 223 ms 에 바뀐다 |
| 과목·교사 불러오기 | 6187 ms | **107 ms** | 아래 "헛기다림" 참고 |
| 칸 하나 입력 | ~2400 ms | **114 ms** | 실측 (3칸 왕복) |
| 저장 확인창 | 1200 ms 고정 | 뜰 때까지 | — |
| 저장 완료창 | 1500 ms 고정 | 뜰 때까지 | — |

칸당 114 ms 는 <b>크롬 확장보다 오히려 빠르다</b>(확장은 폴링 간격 60~80 ms + 고정 sleep 120 ms 라
칸당 0.4 초 안팎으로 추정된다).

`WaitForTimeoutAsync(1200)` 처럼 **무조건 기다리던 것을 조건이 만족될 때까지 폴링**(30 ms 간격)으로 바꿨다.
읽기 자체는 원래 쌌다 — 한 주 56칸을 통째로 읽는 데 9~39 ms 다.

## 왜 고정 대기가 그렇게 비쌌나

칸 하나를 넣을 때 고정 대기가 **두 번** 들어갔다.

```
① 그 주 값 읽기            ~40 ms
② 셀 날짜 교차 확인         ~12 ms
③ 우클릭 → 메뉴 대기      1200 ms  ← 실제 91 ms
④ 항목 클릭
⑤ 값 반영 대기            1200 ms  ← 실제 100~200 ms
⑥ 그 주 값 다시 읽어 검증   ~40 ms
```

칸당 2.4 초가 순수한 낭비였다. 800 칸이면 **32 분**이 그냥 기다림이다.

## 헛기다림 — 안 열리는 메뉴를 기다리는 값

폴링으로 바꾸면 <b>상한값이 곧 손해</b>가 된다. 메뉴가 끝내 안 열리는 날에는 그 상한만큼 통째로 기다린다.

학기 첫 주(08-17~08-23)는 월·화가 개학(08-19) 전이라 메뉴가 안 열린다.
상한을 3초로 뒀더니 카탈로그 한 번 읽는 데 <b>6.2초</b>가 걸렸다 — 고정 대기 때보다 나빠졌다.

두 가지로 고쳤다.

1. 상한을 3초 → **800 ms** (실측 91 ms 의 8배면 넉넉하다) → 1.8초
2. <b>학기 밖 날짜는 아예 찔러 보지 않는다</b> → **107 ms**

2번이 핵심이다. "값이 있는 칸부터 본다"만으로는 부족하다 —
<b>처음 넣을 때는 시간표가 비어 있어</b> 값이 하나도 없다. 날짜로 걸러야 그때도 통한다.

찔러 보는 순서(`TimetableSession.ProbeOrder`):

```
① 학기 안 + 값 있는 칸   (메뉴가 열리는 것이 확실)
② 학기 안 + 값 없는 칸
③ 학기 밖                (①② 가 다 실패했을 때만)
```

## 크롬 확장과 비교

같은 일을 하는 확장(시간표 자동 입력기 0.9.6)도 **입력 방식은 우리와 같다** —
칸마다 우클릭 → 메뉴 → 항목 클릭 → 값 재확인. 나이스가 다른 길을 주지 않는다.

빨랐던 이유는 두 가지였고, 하나는 우리도 가져왔다.

| | 확장 | 우리 |
|---|---|---|
| 대기 | 조건 폴링 (60~80 ms) | ~~고정 1200 ms~~ → **폴링 30 ms** ✅ |
| 실행 위치 | 브라우저 **안**(DOM 이벤트 직접) | CDP로 **바깥**에서 (왕복 비용) ❌ |

두 번째는 구조라 바꿀 수 없다. CDP 왕복은 호출당 대략 3~10 ms 다.

## 더 줄이려면 (아직 안 한 것)

### ① 칸마다 주 전체를 두 번 읽는다 — 좁힐 수 있다

`TimetableCellWriter.WriteAsync` 는 앞뒤로 `ReadCurrentWeekAsync()` 를 부른다.
한 번에 56 칸을 다 읽는데, 정작 필요한 것은 **그 칸 하나**다.

- 이득: 칸당 ~20 ms → 800 칸이면 **16 초**. ② 에서 재 보니 이 정도다.
- 위험: 앞의 읽기는 "화면이 그 사이 바뀌지 않았나"를 보는 안전장치다.
- 값어치: **낮다.** ② 와 같은 이유로 권하지 않는다.

### ② 값 확인을 한 칸만 읽기 — **재 봤더니 값어치가 없다** ❌

값 확인 루프가 30 ms 마다 `ReadCurrentWeekAsync()` 를 부르니, 그 칸 하나만 읽으면
빠를 줄 알았다. 만들어서 재 봤다:

```
0행: 한 칸 13 ms · 주 전체  9 ms
1행: 한 칸  5 ms · 주 전체  9 ms
2행: 한 칸  3 ms · 주 전체  8 ms
```

**차이가 5 ms 도 안 된다.** 주 전체 읽기는 DOM 을 훑는 것이 아니라 CLX 데이터 모델을
한 번에 가져오는 것이라 원래 싸다. 폴링 서너 번이면 칸당 20~30 ms, 800 칸에 20 초 남짓이다.

게다가 DOM 에서 읽은 글자는 `체육 (진두성(thejurio))` 처럼 형태가 미묘하게 달라
값 비교 규칙(`TimetableMenuParser`)을 다시 검증해야 한다. **위험 대비 이득이 없어 하지 않았다.**
만들었던 `ReadCellTextAsync` 는 지웠다 — 다시 시도하지 말 것.

### ③ 메뉴를 열 때마다 항목 20개를 전부 파싱한다

`ReadCatalogAsync` 는 메뉴의 모든 버튼 텍스트를 긁어 `TimetableCatalog` 를 만든다.
입력할 때는 **목표 항목 하나만** 찾으면 된다.

- 이득: 칸당 ~20~40 ms
- 방법: 쓰기 경로에서는 "그 텍스트를 가진 버튼을 눌러라" 한 번으로 끝낸다.
  카탈로그는 실행 시작 전에 한 번만 읽는다(이미 그렇게 하고 있다).
- 값어치: 낮음~중간.

### ④ 여러 칸을 한 번의 JS 호출로 (큰 수술) — 남은 것 중 유일하게 큰 이득

지금은 칸마다 CDP 왕복이 대여섯 번이다. 확장처럼 **브라우저 안에서** 한 주치를
한 번에 처리하는 스크립트를 넣고 결과만 받아오면 왕복이 거의 사라진다.

- 이득: 이론상 칸당 ~100 ms 까지 (지금의 절반 이하)
- 위험: **크다.** 지금은 칸마다 검증하고 실패하면 그 자리에서 멈추는데,
  한 덩어리로 보내면 어디서 틀어졌는지 알기 어려워진다. 나이스 화면이 도중에 바뀌면 더 위험하다.
- 값어치: ①~③ 이 모두 20 초 안팎짜리로 판명됐으니, **더 빠르게 하려면 사실상 이 길뿐이다.**
  다만 안전장치(칸마다 검증·즉시 중단)를 어떻게 지킬지 먼저 설계해야 한다.

### ⑤ 이미 맞는 칸은 애초에 건너뛴다 (이미 함)

주에 들어갈 때 계획을 다시 만들어 `AlreadyMatches` 는 클릭하지 않는다.
두 번째 실행부터는 대부분의 칸이 여기 걸려 훨씬 빠르다.

## 손대면 안 되는 것

- **날짜 교차 확인** (`ReadCellDateAsync`) — 클릭 직전에 그 자리가 정말 그 날짜인지 본다.
  화면이 밀렸을 때 엉뚱한 날에 넣는 것을 막는 마지막 방어선이다. 12 ms 다. 지우지 않는다.
- **입력 후 값 재확인** — 클릭이 먹었다고 값이 들어간 것은 아니다.
- **저장 후 재조회 검증** — 저장 대화상자가 떴다고 저장된 것은 아니다(주마다 한 번).
- **주 단위 저장** — 여러 주를 모아 저장하지 않는다. 실패했을 때 어디까지 남았는지 알 수 없어진다.

## 재는 방법

```csharp
// 메뉴 열고 닫기
sw.Restart();
var cat = await t.Reader.ReadCatalogAsync(row, col);
Console.WriteLine($"{sw.Elapsed.TotalMilliseconds:F0} ms");
```

`docs/schedule` 문서로 파싱만 재는 것과 달리, 이 값은 **나이스에 붙어 있어야** 잴 수 있다.
쓰기 없이 읽기만 해도 메뉴·주차 이동 시간은 그대로 나온다.
